# Phase 1 database foundation

This directory contains the first executable schema migration. It implements private membership, profiles, database-controlled roles, security audit events and private storage reservations. It deliberately does not create exam content, attempts, answer keys, AI jobs, training artifacts or payment tables.

The application uses the public Supabase client key and the signed-in user's session. A service-role key is not needed in the Phase 1 web app. Privileged project setup is performed by the project owner through the Supabase SQL Editor or CLI.

## Schema and access boundaries

| Resource | Browser access |
| --- | --- |
| `profiles` | Verified, active members can read/update their own preferences; ID and creation time cannot be changed |
| `user_roles` | Active members can read their own role; only a trusted SQL operator can assign roles |
| `private_access` | No anonymous or authenticated access; stores the owner's private email allowlist |
| `audit_events` | An active admin with an `aal2` MFA session can read; direct client inserts/updates/deletes are denied |
| `is_active_member()` | Reads authoritative DB membership and email verification, not editable user metadata |
| `has_admin_access()` | Requires active membership, a DB admin role and a verified `aal2` session |
| `record_security_event(event_name)` | Active users can report `login`, `logout`, `password_updated`, or `mfa_verified` as themselves; MFA reports require `aal2` |
| Private storage buckets | Reserved and inaccessible to browser roles until reviewed upload/serving pipelines are added in later phases |

The migration installs a `BEFORE INSERT` trigger on `auth.users` that rejects email addresses absent from the active allowlist. The `AFTER INSERT` trigger creates a profile and a student role; client-provided metadata cannot create admins. Existing users are not silently enrolled. Runtime checks consult the allowlist on every request, so disabling membership is effective with an existing token.

All SQL security-definer functions use an empty search path and fully qualified tables. Profiles have database constraints for locale, target-band half steps, time zone and daily goal. Profile changes, role grants/removals and allowlist changes generate database audit events without storing raw profile values. Allowlist audit entries contain an email hash, which remains personal data for retention purposes. A trusted Auth account deletion cascades through its profile/role rows and clears audit actor foreign keys; audit entity UUIDs can remain until the operator's documented retention cleanup. Phase 1 has no browser account-deletion operation.

The session-event RPC is supplementary, authenticated-client telemetry. It cannot prove that a password changed or that logout completed; Supabase Auth audit logs are authoritative for those actions. It derives the actor from `auth.uid()`, accepts no arbitrary metadata, and suppresses repeated user/action reports within 60 seconds. Profile, role and allowlist audit events are generated by database triggers instead of client reports.

## Apply to a new Supabase project

1. Create a dedicated project. Review `migrations/20261025000100_phase1_foundation.sql` and apply it in the SQL Editor, or link a Supabase CLI project and run `supabase db push`.
2. In **Authentication → Providers**, enable email/password and email confirmation. Keep anonymous sign-in disabled. The application requires a confirmed email before private access is granted.
3. Add the intended person's normalized email to the allowlist in the SQL Editor before signup or Google sign-in. Replace the example address; it is not a seeded account:

   ```sql
   insert into public.private_access(email, active)
   values (lower(trim('your-email@example.com')), true)
   on conflict (email) do update set active = excluded.active;
   ```

4. Complete signup and email confirmation through the app. Google OAuth also requires the provider configuration described in the root README. The database trigger applies to both methods.
5. To grant the intended operator the admin role after the account exists, run a reviewed SQL operation:

   ```sql
   update public.user_roles
   set role = 'admin', assigned_at = now()
   where user_id = (
     select id from auth.users where lower(email) = lower('your-email@example.com')
   );
   ```

6. Enable TOTP enrollment and verification in Supabase Auth MFA settings. The admin must enroll and verify an authenticator in the app before accessing admin pages.
7. Configure the exact site origin and redirect allowlist in Supabase Auth. Local defaults are `http://localhost:3000/auth/callback` and `http://localhost:3000/auth/confirm`; add the exact production domain when deploying. Avoid wildcard production redirects.
8. Put the project URL and public client key in the web environment template. Do not put database passwords, OAuth client secrets or a service-role key in source control or frontend variables.

`enable_signup = true` is necessary for allowlisted self-signup/Google creation; the database trigger rejects everyone else. For an invite-only operational process, disable open signup in the Supabase dashboard and use the project's invitation workflow after allowlisting. Whichever approach is selected, verify real end-to-end account creation before release. Supabase's built-in email sender has delivery restrictions and quotas; configure an allowed sender if needed rather than claiming email delivery was tested without an account.

For an existing user in a project created before this migration, allowlist the email, then explicitly provision only that selected user's `profiles` and `user_roles` rows using a reviewed SQL operation. Do not bulk-enroll all existing accounts. New projects are recommended for this foundation. A selected existing account can be provisioned as a student using:

```sql
begin;
insert into public.profiles(user_id)
select id from auth.users where lower(email) = lower('your-email@example.com')
on conflict (user_id) do nothing;
insert into public.user_roles(user_id, role)
select id, 'student' from auth.users where lower(email) = lower('your-email@example.com')
on conflict (user_id) do nothing;
commit;
```

Verify that exactly the intended account was selected. This does not confirm an unverified email or grant the admin role.

To revoke access, set the allowlist record's `active` value to `false` through the SQL Editor. Also revoke active sessions through Supabase Auth when immediate provider-level signout is needed. The app and RLS already deny private data once membership is inactive.

## Local database and tests

The checked-in `config.toml` supports a local Supabase stack. Install the Supabase CLI and a compatible Docker runtime before using it. From the repository root:

```sh
supabase start
supabase db reset
supabase test db
```

`supabase db reset` recreates the **local** development database and applies migrations; do not run it against data you need to keep. No seed data is enabled. Allowlist your development email manually. Local confirmation messages are available in the local Supabase email inbox rather than being sent to real recipients.

`tests/database/phase1_rls.test.sql` uses pgTAP and transaction-scoped synthetic users. It tests two-user isolation, denied signup, email verification, runtime revocation, self-promotion, MFA, immutable audit events, ownership/field validation and reserved storage boundaries. It rolls back the fixture data and temporary policies. Run it on a local or disposable staging database, not the production project.

The web repository also includes `tests/database/foundation.test.ts`, which runs the actual migration under PGlite/PostgreSQL using minimal Supabase Auth and Storage schema stubs. Run it with:

```sh
npm run test -- tests/database/foundation.test.ts
```

Passing these tests verifies PostgreSQL policy behavior locally. It does not verify the hosted Auth service, Google OAuth, email delivery, Storage HTTP API, provider claims, MFA flow, Netlify deployment or project configuration. The full pgTAP suite and real-account smoke tests remain required on the configured Supabase project before release.

After changing migrations, regenerate `src/types/database.ts` from a migrated project with the Supabase CLI and review the resulting contract. The Phase 1 file is a handwritten contract matching the migration.

## Storage and later phases

The migration reserves `content-private`, `student-uploads-private` and `speaking-recordings-private`, with private visibility, MIME allowlists and maximum object sizes. It checks that Supabase's Storage tables have RLS enabled before installation. Restrictive policies explicitly deny browser access to these three buckets even if an existing project has a broad permissive policy. The policies are intentionally replaced only when later phases implement validated uploads, scoped access and retention.

Do not loosen storage policies just to make a future upload UI work. Phase 1 does not include uploads, signed URLs, recordings, QR sessions or AI ingestion. File-type declarations alone are not validation of file contents.

## Operational checklist and migration recovery

- Configure separate development/staging and production projects; never share real student data with test fixtures.
- Keep Supabase Auth rate limits enabled. Establish provider quotas and sender limitations before inviting users.
- Record backup/export and restoration procedures appropriate to the actual plan. Free-plan backup availability has not been assumed or verified by this migration.
- Define retention periods for account records, audit metadata, Auth logs and backups before operational use. Client audit mutation is prohibited; retention cleanup is an explicitly authorized operator responsibility.
- Apply the migration to a disposable project first, run the tests, then apply it to the intended project. A failed migration should be diagnosed before retrying; never delete user records merely to make a migration pass.
- Use reviewed forward migrations or restore a tested backup for production recovery. There is no automatic destructive down migration. Local `db reset` is reserved for disposable development data.
- Keep the source specification documents unchanged. Add future schema features as new versioned migrations only after their phase is approved.

### Backup and restore drill before operational use

1. Choose a backup/export mechanism supported by the configured Supabase plan. Record who can decrypt/access the backup, its retention period and the expected recovery point. Keep database dumps and export credentials outside this repository.
2. Include schema, policies, functions, application data and the necessary Auth configuration/data in the documented recovery plan. Back up actual Storage object bytes separately when uploads exist; database metadata alone is not the media file backup.
3. Restore into a separate disposable project, never over the only working database. Reapply or verify the exact migration history and confirm the application tables and Storage tables still have RLS enabled.
4. Run the pgTAP suite, then real Auth smoke tests with two staging accounts: one account must never read/update the other's profile, unallowlisted signup must fail, revoked membership must lose access and an admin without MFA must not read audits.
5. Check that bucket visibility remains private, browser object operations remain denied in Phase 1 and audit rows have not been dropped unexpectedly. Verify any future restored files against their manifest separately.
6. Record the restore duration, latest recovered data timestamp, checks performed and failures. A plan on paper is not a completed restore drill. No restore has been executed against a hosted project by this implementation task.
